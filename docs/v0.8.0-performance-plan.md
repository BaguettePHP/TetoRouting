# v0.8.0 Performance Plan

## Purpose

v0.8.0 will reduce the remaining cost of dynamic route matching without trading away shared-nothing performance. The primary target is the linear scan over variable-route candidates. Public routing behavior, declaration-order precedence, arbitrary parameter regular expressions, and extension handling must remain compatible with v0.7.0.

## Current baseline

The v0.7 optimization branch has already improved construction and matching without increasing memory materially.

- Synthetic workloads still scale almost linearly for late dynamic matches and misses: approximately 16.6 µs with 100 candidates and 157.7 µs with 1,000 candidates.
- Against v0.7.0, shared-nothing construction and constructor-plus-one-match workloads are faster in the private corpus, while late matches and misses show the largest hot-path gains.
- Against v0.6.0, shared-nothing workloads are approximately 10–15% faster in the private corpus. Hot fixed and early matches remain approximately 5–6% slower, while middle, late, and miss cases are approximately 21–41% faster.
- Router memory usage is effectively unchanged.

The benchmark suite must continue to report construction-only, constructor-plus-one-match, and repeated-match results separately. Repeated-match improvements cannot justify a regression in the normal PHP-FPM/prefork case.

## Primary bottleneck

`Router::match()` currently narrows variable routes by segment count and then walks every candidate. It rejects mismatched literal segments before calling `Action::match()`, but the candidate scan remains `O(N × S)` where `N` is the number of same-depth candidates and `S` is the number of path segments.

The v0.8.0 target is an ordered discrimination index:

```text
segment count
  └ HTTP method
      └ parameter-position shape
          └ literal-segment key
              └ declaration-ordered route IDs
```

For example, `/users/:id` and `/:tenant/posts/:id` have different parameter-position shapes. At match time, the request supplies the literal key for each shape, so only candidates whose literal segments agree reach regular-expression matching.

If `G` is the number of shapes and `K` is the number of candidates that survive literal discrimination, the expected lookup cost becomes approximately `O(G × S + K × regex)`. The worst case remains linear when every route has the same shape and literal segments.

## Compatibility constraints

### Declaration order

Overlapping parameter regular expressions are valid, and the first declared matching route wins. Every indexed candidate receives a monotonically increasing declaration ID. Candidate lists from multiple matching shapes must be merged by that ID before regular expressions are evaluated.

### Extensions

Extension-aware routes and routes that treat a dot as part of the final path segment require separate lookup representations:

- extension-aware: match the base segment and extension independently;
- extension-opaque: retain the complete final segment, including dots.

A single normalization path would change existing behavior.

### Mutable match state

`Action` currently contains both compiled route data and mutable result state in `param` and `extension`. An index may reference route definitions, but it must not cache or share match results. Repeated matches must retain the current state-reset behavior.

### Public interface

v0.8.0 keeps `Router` construction, `Router::match()`, and the returned `Action` shape compatible. A separate immutable match-result type and private compiled-route representation are deferred until a release that permits an interface change.

## Implementation phases

### Phase 1: Prototype the ordered shape index

Build a benchmark-only prototype before changing production lookup. Measure:

- index construction time;
- constructor-plus-one-match time;
- early, middle, late, and miss matching;
- number of distinct shapes and surviving candidates;
- memory usage.

Compare the synthetic 100- and 1,000-candidate workloads and the private corpus. Do not copy private route names or structure into repository artifacts.

### Phase 2: Integrate the index behind `Router`

Keep the index private to `Router`; do not introduce a strategy interface until a second implementation is needed. Preserve the existing fixed-route hash table and use the new index only for variable routes.

Add regression coverage for:

- overlapping regular expressions and declaration order;
- routes accepting multiple methods;
- extension-aware and extension-opaque routes;
- repeated matches and mutable `Action` state;
- same-depth routes with different literal positions;
- worst-case routes that share one shape.

### Phase 3: Remove quadratic parameter accumulation

`Action::match()` currently copies the parameter array after every captured parameter. Accumulate captures in a local array and assign it once after the full route succeeds. This changes parameter collection from approximately `O(P²)` copying to `O(P)`, where `P` is the number of parameters, while preserving failure-state behavior.

This is secondary to candidate indexing because most real routes contain few parameters.

### Phase 4: Evaluate generated routers for shared-nothing runtimes

If construction remains material after indexing, prototype a build-time compiler that emits fixed lookup tables and the ordered dynamic index as PHP code. OPcache can then retain the generated opcodes across requests without APCu or shared userland objects.

Generated artifacts must have deterministic invalidation and must expose the same matching interface. This phase is optional for v0.8.0 and proceeds only if constructor-plus-one-match measurements justify its operational complexity.

## Alternatives considered

### Segment trie or radix tree

A trie offers lookup proportional to path length for literal routes, but arbitrary parameter regular expressions introduce ordered branching and backtracking. The existing `CommonPrefixTrieRouter` supports a smaller placeholder model and is useful as a reference, but it is not a compatible replacement for `Router`.

### Combined PCRE dispatch

Combining candidates into a single alternation may move work from PHP into PCRE, but capture numbering, declaration order, compilation cost, and diagnostics become significantly more complex. Reconsider it only as part of generated routers.

### Method-only bucketing

Method buckets are low risk and may be included in the shape index, but they only help route sets containing mixed methods and do not address the main same-method scan.

## Acceptance gates

The shape index may ship only when all of the following hold:

- no routing behavior changes in PHPUnit and mutation tests;
- PHPStan and ECS pass;
- constructor-plus-one-match does not regress materially in synthetic or private-corpus measurements;
- 1,000-candidate late match and miss improve from roughly 158 µs toward 25 µs or less;
- construction overhead remains below 5%, unless the total constructor-plus-one-match result is still faster;
- memory growth remains bounded and is reported explicitly;
- declaration-order, extension, and repeated-match cases have direct regression coverage;
- benchmarks record PHP version, OPcache/JIT settings, process count, iterations, and distribution rather than only a single mean.

## Deferred interface deepening

A future release should separate immutable compiled route data from mutable match results. That would permit packed internal tables, winner-only `Action` materialization, safe caching, and clearer ownership of `param` and `extension`. It is deliberately not required for the v0.8.0 index so that the algorithmic improvement can be evaluated independently of an interface migration.
